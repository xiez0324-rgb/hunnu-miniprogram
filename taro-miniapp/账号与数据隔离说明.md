# 账号与数据隔离说明（家长端 / 老师端）

> 工程：二号开发版本 / taro-miniapp（大学城家教小程序）
> 云环境：微信云开发 `[环境 ID 见本地 .env]`
> 更新时间：2026-09-12

---

## 一、一句话结论

同一个微信号在小程序里是**同一个微信身份（同一 OPENID / UNIONID）**，但家长与老师的**档案与业务数据是物理分表、各自独立的**：

- 家长档案 → `parent_users`，主键 `userId = parent_<openid>`
- 老师档案 → `teacher_users`，主键 `userId = teacher_<openid>`

因此「同一身份在云端是否统一」的答案是：**身份根统一（OPENID），业务档案不统一（按角色分表）**。同一个微信既当家长又当老师时，等于持有两套互不覆盖的档案，切换身份不会串数据、不会互相覆盖。

---

## 二、身份标识体系

| 标识 | 含义 | 生成方式 | 用途 |
|---|---|---|---|
| `OPENID` | 小程序维度用户唯一标识 | 微信下发（`cloud.getWXContext().OPENID`），**客户端不可伪造** | 所有权限校验的**唯一可信来源** |
| `UNIONID` | 开放平台维度唯一标识 | 微信下发（需绑定开放平台，未绑定时为空） | 跨应用身份预留，落库在用户档案 |
| `userId` | 平台账号主键 | `${role}_${openid}`（如 `parent_oX...`、`teacher_oX...`） | 分表主键，保证两表永不冲突 |
| `demandId` | 需求单业务号 | 8 位去混淆随机码（剔除 `0/o/1/l/i`），创建时查重 | 全站关联需求（详情/报名/订单） |
| `teacherId` | 老师业务标识 | 真实报名老师 = `t_` + `openid` 后 6 位；种子老师为 `t1`~`t6` | 报名记录、订单、简历关联 |
| `applicationId` | 报名记录 id | `applications` 文档 `_id` | 取消报名等操作定位 |
| `orderId` | 订单 id | `matches` 文档 `_id` | 管理端订单流转/撤回 |

**关键约定**：业务 id（`demandId`/`teacherId`/`orderId`）是**可被客户端传入的参数**，因此任何写接口都必须再校验其归属，不能只凭 id 信任调用方（本轮已修复 3 处该问题，见第七节）。

---

## 三、家长端 / 老师端的数据存储口径

| 维度 | 家长端 | 老师端 |
|---|---|---|
| 档案表 | `parent_users` | `teacher_users` |
| 主键 | `userId = parent_<openid>` | `userId = teacher_<openid>` |
| 档案字段 | nickname / gender / phone / wechat / area / role / unionid / notifyPrefs | 同左（字段结构一致，表分离） |
| 业务数据 | `demands`（需求单，`_openid` 归属） | `applications`（报名，`_openid` 归属）、`resumes`、`verifications` |
| 共享撮合数据 | `matches`（订单）、`inquiries`（咨询）、`fee_records`（费用） | 同左 |
| 订阅偏好 | `parent_users.notifyPrefs` | `teacher_users.notifyPrefs` |

**同一微信同时是家长 + 老师时**：

- 两条档案分别落在两张表，`userId` 前缀不同 ⇒ 永不覆盖；
- `getProfile` / `updateProfile` / `login` / `notifyPref` 均**必须显式传 `role`**，由 role 决定操作哪张表，不存在「默认落到某张表」的隐式行为（`getProfile`/`updateProfile`/`notifyPref` 仅在 role 非法时兜底为 teacher，前端始终显式传）；
- 「我的报名」与「我的需求」是两套不同查询：老师查 `applications`，家长查 `demands`，均按 `_openid` 过滤，同一个人在两端看到的是各自角色的数据，不交叉。

## 四、全流程处理逻辑

### 4.1 首次登录 → 自动建档

```
小程序端 wx.login 获取 code
        ↓
云函数 login({ role, nickname?, code? })
        ↓
cloud.getWXContext() → OPENID / UNIONID（服务端可信，客户端无法伪造）
        ↓
role → 目标表（parent_users / teacher_users）
        ↓
按 { userId = `${role}_${openid}`, _openid: openid } 双条件查询
        ↓
┌─ 已存在 → 回读 + 默认昵称兜底（历史演示名「张同学/同学」视为未命名并纠正）
└─ 不存在 → add 建档（_openid/userId/role/nickname/phone/gender/unionid）
             并发冲突（add 失败）→ 回读既有账号，保证幂等不重复建号
        ↓
返回 { openid, unionid, userId, nickname, avatar, role, phone, gender }
```

- **集合缺失容错**：首次部署/误删集合时，`login`/`getProfile`/`updateProfile` 会 `createCollection` 后重试一次（幂等）。
- **初始态空白**：新家长 `nickname = ''`、新老师 `nickname = '同学'`，`phone`/`gender`/`notifyPrefs` 均为空，不写入任何演示数据。

### 4.2 身份切换（同一微信双角色）

```
「我的 → 切换身份」
   ↓ 本地：store.user.role 立即切换（UI 即时响应）
   ↓ 云端：callFunction('login', { role })   ← 为新角色建档/回读（幂等）
   ↓ 云端：refreshProfile(role) → getProfile({ role }) → 回填该角色昵称/电话/区域
```

切换只影响「当前操作的角色上下文」，**不会迁移或复制数据**，两个角色的历史业务数据始终各自保留。

### 4.3 读流程（按归属过滤）

| 接口 | 身份来源 | 过滤条件 | 说明 |
|---|---|---|---|
| `getMyData(parent)` | OPENID | `demands._openid = openid` 且 `status ≠ 已下架` | 家长只能看到自己的需求 |
| `getMyData(teacher)` | OPENID | `applications._openid = openid`（+ 可选 status） | 老师只能看到自己的报名 |
| `getMyResume` | OPENID | `resumes._openid = openid` | 本人简历 |
| `getProfile` | OPENID + role | `{ userId, _openid }` 双条件 | 本人当前角色档案 |
| `getApplicants` | OPENID | 先校验 `demands._openid === openid` | 报名名单仅需求发布者可见 |
| `getDemandDetail` | OPENID | 公开脱敏数据 + 发布者专属字段 | 见第六节 |
| `getDemands`（广场） | OPENID | `status=进行中` + `auditStatus=已通过` + `recruiting ≠ false` | 脱敏后对登录用户开放 |

### 4.4 写流程（归属校验）

| 接口 | 归属校验 | 写入集合 |
|---|---|---|
| `createDemand` | `_openid` 由服务端注入 | `demands` |
| `applyDemand` | `_openid` 由服务端注入；仅允许「审核通过 + 未停止招募」的需求 | `applications` + `demands.applicants` |
| `cancelApplication` | 读原记录校验 `cur._openid === openid` | `applications` |
| `confirmMatch` | **本轮新增**：校验 `demands._openid === openid` + 被确认老师存在活跃报名 | `matches` + `applications` |
| `cancelConfirm` | **本轮新增**：校验 `demands._openid === openid` | `applications` + `matches` |
| `requestTeacherInfo` | **本轮新增**：校验 `demands._openid === openid` | `inquiries` |
| `saveResume` | 按 `_openid` upsert | `resumes` |
| `submitVerification` | `_openid` 由服务端注入 | `verifications` |
| `updateProfile` | `{ userId, _openid }` 双条件定位，白名单字段，**role 不可改** | `parent_users` / `teacher_users` |
| `notifyPref` | `{ userId, _openid }` 双条件定位 | 对应角色表 |

### 4.5 管理端

管理端所有云函数统一走 `requireAdmin(event)`：`token → uid → openid` 三级匹配 `admins` 集合（`enabled: true`），失败抛 `err.code='FORBIDDEN'`。部分敏感操作再叠加权限位校验（如 `adminWithdrawOrder` 的 `canManageOrders`：`level` 为 root/admin，或 `perms/permissions` 含 `order:manage|orders|order|*`，或 `orderManage === true`）。管理端可跨用户读取全量数据，属预期行为。

## 五、数据可见性边界

| 数据 | 可见范围 | 落地规则 |
|---|---|---|
| 需求单基础信息（年级/需求/时段/预算/区域/备注） | 所有登录用户（脱敏撮合信息） | `getDemands` 剔除 `phone`、`_openid` |
| 家长联系电话 `phone` | **仅需求发布者本人** | `getDemandDetail` 对非发布者置空 |
| 需求归属 `_openid` | 不对外下发 | `getDemandDetail` 对非发布者删除该字段 |
| 报名名单（老师快照） | 仅需求发布者 + 管理端 | `getApplicants` 归属校验 |
| 老师简历 / 学籍材料 | 本人 + 管理端；报名后按快照展示给对应家长 | `_openid` 过滤 / 快照脱敏 |
| 订单（`matches`） | 双方 + 管理端 | 管理端接口 + 归属校验 |
| 费用台账 | 仅管理端 | `requireAdmin` |

**前端不直接读写数据库**：业务数据全部经云函数，客户端凭 `Taro.cloud.callFunction` 调用，无法绕过云函数里的归属校验。（`services/cloud.ts` 的 `getDatabase()` 当前无调用点，属遗留代码。）

## 六、隔离回归清单

| # | 场景 | 预期 |
|---|---|---|
| 1 | 家长 A 登录，查看「我的需求」 | 只出现 A 自己的需求 |
| 2 | 家长 A 传家长 B 的 `demandId` 调 `confirmMatch` / `cancelConfirm` / `requestTeacherInfo` | 返回「无权操作该需求」，**不产生任何写入** |
| 3 | 老师 X 查看「我的报名」 | 只出现 X 自己的报名 |
| 4 | 老师 X 传他人 `applicationId` 调 `cancelApplication` | 返回「无权操作该报名记录」 |
| 5 | 同一微信切换为老师身份 | 看到老师档案与报名数据；切回家长身份看到家长档案与需求数据，两者不混淆 |
| 6 | 新增家长账号首次进入各页面 | 我的需求为空、未读角标为 0、消息通知为空态、无演示老师入口 |
| 7 | 新增老师账号首次进入各页面 | 广场为空、报名为空、简历为空、认证为空、昵称为「同学」 |

以上 1~4、6~7 已由离线桩测试覆盖（23 项断言全部通过，见《功能迭代测试报告》8.6）。

## 七、已知残留风险与建议

| # | 风险 | 说明 | 建议 |
|---|---|---|---|
| 1 | `applyDemand` 报名上限/重复报名为 check-then-act | `count` 与 `add` 非原子；并发下理论上可突破 5 条上限或产生重复报名 | 重复报名用唯一索引 `(_openid, demandId)` 兜底（云开发事务不支持 `where`，无法用事务包住 count+add）；上限改为计数原子自增 + 补偿 |
| 2 | 高频条件缺索引 | `demands(status,auditStatus,createTime)`、`applications(demandId,teacherId,status)`、`matches(demandId,status)` 等 | 在云开发控制台补齐索引 |
| 3 | 老师端报名列表无显式上限 | 服务端默认 100 条，数据量增长后历史被截断 | 改 `limit + 分页` |
| 4 | `adminDashboard` 费用汇总全表取出 | 台账增大后单次调用耗时/内存上升 | 改 `count()` / 聚合 |
| 5 | 管理端账号可多人共用 | 后登录会替换 `currentToken`，旧设备被顶下线（已做失效提示） | 如需严格隔离，按人分配管理员子账号 |
| 6 | `login` 失败时前端本地降级登录 | 会生成临时 openid 的本地会话（云端无账号） | 低风险；如需严格隔离可改为直接报错阻断 |
